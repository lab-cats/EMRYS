## Source-grounded discoveries

### F01 — Authored and normalized input

The [Project schema](../../src/emrys/contracts/schemas/orchestration/v1/project.schema.json) closes `reference` to FASTA, GTF, and `star_index`; the latter is a direct reference to the [Reference schema's](../../src/emrys/contracts/schemas/orchestration/v1/reference.schema.json) closed numeric object. [Normalization](../../src/emrys/orchestration/run_coordinator/normalization.py) hashes the two reference files and carries only the three numeric STAR policy fields. Adding a directory to `star_index` would affect authored and normalized shapes together and be rejected by the current numeric normalizer. Named creation derives and freezes all three settings; existing hand-authored Projects that omit chromosome-bin nbits normalize to 18 without rewriting them ([configuration guide](../../configs/README.md)).

Project admission computes one shared Reference before its Analysis loop. The normalized Reference v1 and [Attempt authored-path record](../../src/emrys/contracts/schemas/orchestration/v1/workflow_attempt.schema.json) are also closed. Carrying a supplied directory, member inventory, or authored spelling into them requires a reviewed schema/reader and compatibility decision; the Project YAML alone is not a substitute for immutable Run and Task binding. Current generated records must remain readable with their original meaning. The [Run implementation closure](../../src/emrys/orchestration/run_coordinator/run_implementation.py) includes the Reference and Attempt schema files, so even optional schema edits can change generated Run implementation identity. A stable generated input shape alone does not promise a stable Run ID across installations.

**Proposed direction:** put one optional supplied-source declaration on Project `reference`, not on each Analysis, while retaining `star_index` as the numeric construction/expected-parameter policy. A possible closed object has an explicit directory and provenance sidecar path; exact field names, schema versioning, and whether a separate sidecar is sufficient remain open public-contract decisions. Keep generated mode as the absence of this optional declaration. Decide whether guided creation keeps the existing derived numeric values and compares them with provenance or admits values from the provenance under a reviewed policy. New public fields require explicit approval.

### F02 — Content and historical provenance

The [Stage 00a validator](../../src/emrys/stages/star_index/validator.py) checks seven identities: required members, FASTA and GTF paths recorded in genomeParameters.txt, ordered contig names and lengths, and the three numeric settings. It does not compare FASTA/GTF content hashes to build-time hashes, fingerprint every index member, or establish the exact producer release. A validation mismatch may appear as a failed report row rather than a nonzero process exit; a caller must inspect every required row. The current Run Task separately invokes semantic all-pass after validation, so the standalone command's exit behavior is an admission concern, not an identified Run bypass.

[STAR 2.7.11b writes](https://raw.githubusercontent.com/alexdobin/STAR/2.7.11b/source/genomeParametersWrite.cpp) source path strings, settings, and output sizes, without source-content digests. Matching present-day paths and contig lengths cannot prove which exact sequence and annotation bytes generated a historical index. [Project normalization](../../src/emrys/orchestration/run_coordinator/normalization.py) hashes the current FASTA/GTF bytes, but those hashes have no retained build-time counterpart for an external index.

The validator lexically absolutizes native `genomeFastaFiles` and `sjdbGTFfile` path strings against a supplied parameter base and compares them with the current Project paths; it does not resolve symlinks. A relocated index and content-identical current references can therefore fail its path rows. Preserve the existing seven check IDs and generated-mode meaning; decide whether supplied admission requires original paths or treats those native paths as historical corroboration while comparing retained build-time hashes with present bytes. In the latter case, supplied admission cannot simply require all seven old rows to pass unchanged.

An EMRYS-generated Step 00a Run already offers one candidate evidence chain: [materialization](../../src/emrys/orchestration/run_coordinator/materialization.py) declares FASTA/GTF Task inputs and STAR arguments; [Task execution](../../src/emrys/orchestration/run_coordinator/task.py) checks and hashes inputs around execution, records command outcomes and output hashes, and publishes a verified marker only after success. Publication includes extra top-level index members beyond the fifteen declared files, and later verified-Task admission rehashes the complete recorded roster. The observed runtime STAR binary is bound through Doctor and lifecycle admission. That record remains tied to its Run and paths; copying its JSON beside a detached directory does not transfer its authority. The executable is observed before workflow, not atomically at STAR spawn, so this is not proof against a concurrent binary writer.

For a foreign producer, distinguish trusted producer-time attestation from a post hoc supplier manifest. A credible origin record needs pre-build FASTA/GTF sizes and hashes with a source-stability rule, producer executable digest plus release/build identity, one closed effective recipe including parameter files and defaults, observed successful STAR completion, and a post-success name/size/hash inventory of every index member. Bind that record outside the index directory under a reviewed custody rule, then rehash present source files and every present member and cross-check native metadata and runtime compatibility. The [existing reference-provenance inventory](../../src/emrys/evidence/reference_provenance/_reference_inventory.py) allows unknown expected hashes and requires only one index-file row, so it is not this authority. STAR [writes genomeParameters.txt before its final large members](https://raw.githubusercontent.com/alexdobin/STAR/2.7.11b/source/Genome_genomeGenerate.cpp); native metadata can exist after an incomplete build.

**Proposed direction:** decide how an existing verified EMRYS Run can be referenced without detaching its evidence, and which foreign actors/custody records can make an attested historical claim. Current bytes, native metadata, a producer log, and a newly written post hoc manifest can establish present compatibility but cannot establish which exact historical FASTA/GTF bytes STAR read. If neither accepted provenance route exists, fail historical-source admission under the accepted outcome rather than silently weaken it.

### F03 — Exact version and closed recipe

The installed [runtime policy](../../src/emrys/resources/runtime/runtime_policy.tsv) requires STAR `2.7.11b`. [Doctor](../../src/emrys/orchestration/run_coordinator/doctor.py) records the observed runtime version, canonical executable path, and binary SHA-256; [processing identity](../../src/emrys/contracts/orchestration/application_model.py) binds tool content. These facts identify the admitted runtime, not the external producer.

STAR's [versionGenome default](https://raw.githubusercontent.com/alexdobin/STAR/2.7.11b/source/parametersDefault) is `2.7.4a` for release `2.7.11b`: it marks the earliest compatible index version, not the exact producer release. Requiring it to equal `STAR --version` would reject a normal index. The native [metadata writer](https://raw.githubusercontent.com/alexdobin/STAR/2.7.11b/source/genomeParametersWrite.cpp) includes an override-command line; the tagged [parameter reader](https://raw.githubusercontent.com/alexdobin/STAR/2.7.11b/source/Parameters.cpp) constructs that line from user overrides rather than a closed effective recipe. A retained producer `Log.out` reports release/build text but remains supplier evidence, not cryptographic proof linking that release to these bytes.

Other index-affecting settings and inputs include suffix-array sparsity, genome transformation, extra splice-junction sources, and GTF feature/tag choices. One concrete gap is `genomeSuffixLengthMax`: the tagged [generator](https://raw.githubusercontent.com/alexdobin/STAR/2.7.11b/source/Genome_genomeGenerate.cpp) uses it during suffix-array construction, yet the metadata writer has no dedicated row for it. A second gap changes a required member: tagged STAR's [GTF parser](https://raw.githubusercontent.com/alexdobin/STAR/2.7.11b/source/GTF.cpp) uses gene-name and gene-type tag settings to populate attributes that the [geneInfo.tab writer](https://raw.githubusercontent.com/alexdobin/STAR/2.7.11b/source/GTF_transcriptGeneSJ.cpp) emits, while the native metadata writer omits dedicated rows for those settings. The [current worker](../../src/emrys/stages/star_index/step_00a_build_star_index.sh) passes the three explicit Project values to STAR genome generation.

The generator normally moves `Log.out` into the index directory and records release/build text there, but the move can fail and the current fifteen-member contract does not require that file. A retained log may corroborate the producer claim; as supplier-controlled text it cannot alone authenticate the executable, source bytes, or completed index. The native writer's `genomeFileSizes` covers selected output sizes, not a complete digest inventory.

**Open decision:** define the supported externally generated recipe, including all effective index-affecting settings and inputs, parameter-file overrides, source multiplicity, acceptable defaults, and rejected transformations or additions. Decide whether exact producer identity means a declared release, source commit, or attested executable digest; matching `STAR --version` text alone does not establish producer code identity. For a first fail-closed route, require a declared producer release compatible with the admitted runtime STAR `2.7.11b` under a reviewed rule. Keep the producer claim, native compatibility marker, and observed runtime binary identity separate.

### F04 — Directory closure and change detection

The [stage contract](../../src/emrys/stages/star_index/CONTRACT.md) lists fifteen nonempty regular members as the protected minimum and permits additional native files. The [alignment worker](../../src/emrys/stages/star_alignment/step_01_star_align.sh) passes the entire directory as genomeDir. The Stage 00a producer accepts an empty extra regular file, while [Stage 01 Task directory admission](../../src/emrys/orchestration/run_coordinator/task.py) rejects any empty member. Supplied-mode policy must settle this existing cross-boundary difference without silently changing generated-mode behavior.

The Task boundary enumerates and content-snapshots every top-level input-directory member when that directory is planned as a Task input, then rechecks at producer entry, after the producer and validator, and during later verified-Task admission. It does not bind an external directory into Project or Run identity or continuously freeze shared storage while STAR reads. The [shared input helpers](../../src/emrys/libraries/validation/inputs.py) support stable, no-follow directory listing and streamed hashing. Project normalization accepts lexical absolute paths, whereas Task input directories must be real canonical paths; external admission should diagnose that mismatch before creating a Run.

**Proposed direction:** admit a deterministic ordered inventory of every observed top-level member, require the fifteen named nonempty files, and bind each admitted name, size, and SHA-256. Set an explicit policy for symlinked paths or ancestors, nonregular and nested entries, zero-length extras, and hardlinked mutable files. Use no-follow directory enumeration plus before/after directory and member identity checks around hashing; a stable listing alone is insufficient. Keep the provenance record outside the indexed directory to avoid a self-referential inventory. Recheck membership and bytes at existing trust boundaries. Decide whether the operator must provide an immutable/read-only snapshot for execution or accepts the stated transient-writer risk; boundary rechecks do not prove the exact bytes STAR consumed. Measure repeated hashing cost on representative shared storage before a performance claim.

### F05 — Graph and worker authority

The [semantic stage map](../../src/emrys/contracts/STAGE_MAP.md) describes external inputs as having no producer node and currently has a direct Stage 00a-to-01 index edge. The [built-in profile](../../src/emrys/workflow/contracts/local_cmh_v2.json) requires construction and its artifacts. [Materialization](../../src/emrys/orchestration/run_coordinator/materialization.py) always builds a Stage 00a producer command into a create-absent Run directory; Stage 01 reads the resulting path.

At planning, [profile validation](../../src/emrys/contracts/orchestration/artifact_inventory.py) compares processing edges with the installed task graph. The [Snakemake graph](../../src/emrys/workflow/Snakefile) then checks a static complete processing-owner projection and builds rules from installed processing tasks. The [expected-Task roster](../../src/emrys/orchestration/run_coordinator/_inspection_admission.py) derives from immutable functional specification, while materialization builds its commands from installed processing tasks. Stage 01 publication currently reads its index input from the 00a Run output path. Removing 00a from only the Run profile would fail graph admission or leave a mismatched plan, Stage 01 input, and verified-Task tree. Historical generated Run profiles need their existing read-only interpretation. A schema-readable old Run is not automatically resumable after installation changes: resume requires a byte-equal Run binding that includes implementation content ([implementation closure](../../src/emrys/orchestration/run_coordinator/run_implementation.py)).

[Normalization](../../src/emrys/orchestration/run_coordinator/normalization.py) loads one generated processing base profile, then [composes](../../src/emrys/analyses/__init__.py) a selected Analysis module tail separately for each Analysis. A supplied-mode processing projection should be decided once from the admitted Project Reference before those compositions, so every Analysis receives the same conditional base. The installed generated profile feeds `processing_tasks()` for materialization and Snakemake, while `processing_artifact_templates()` feeds the reporting adapter registry. Replacing that profile with a supplied-only one would break generated and historical readers. A conditional projection must keep owner tasks, semantic owner keys, required owner keys, edges, and artifact templates consistent under existing profile validation.

**Proposed direction:** select one source mode in the immutable plan and carry it through the approved stage input/edge representation, a validated conditional projection from the installed generated base, expected Tasks, materialization, Snakemake rules, and Stage 01 index input. Supplied mode must not schedule construction or invent a successful Stage 00a Task. Preserve the generated 00a-to-01 edge and historical read-only interpretation; keep current same-install resume rules unless a separate compatibility design is approved. Reuse existing graph authorities rather than adding a parallel execution backend.

### F06 — Analysis, Run, and processing reuse

The [application model](../../src/emrys/contracts/orchestration/application_model.py) derives reference scope from FASTA/GTF hashes. Execution Plan and processing compatibility currently bind the three STAR values and runtime toolchain, but no supplied-index digest. They also bind the full processing resource declaration, including Step 00a thread and memory controls that [resource admission](../../src/emrys/orchestration/run_coordinator/resource_policy.py) still requires. The [implementation closure](../../src/emrys/orchestration/run_coordinator/run_implementation.py) includes Stage 00a implementation files in processing identity even if a future supplied graph never executes that owner. Decide deliberately whether these unused generated-mode inputs remain identity-significant in supplied mode or are conditionally excluded, with corresponding public policy and compatibility effects. Otherwise changing only an unused 00a control could create a distinct supplied Run and block reuse.

The [Attempt continuity fields](../../src/emrys/orchestration/run_coordinator/_inspection_attempts.py) omit authored paths, yet [resume](../../src/emrys/orchestration/run_coordinator/control.py) recomputes the Run binding and retains verified Tasks with their original dispatch input bindings. A content-identical supplied index at a new path therefore needs an explicit policy for new and retained Tasks; path relocation must not silently change the Run plan.

[Processing reuse](../../src/emrys/orchestration/run_coordinator/inspection.py) requires compatible Reference and processing identities and collects content-bound verified Task outputs for product remapping. A supplied index has no 00a Task output, but its Stage 01 verified Task inputs could carry directory evidence under existing Task admission. Determine whether that evidence plus immutable source identity suffices for `--from-processing-run`; add no separate cross-Run representation without a concrete reader need. [Reporting projection](../../src/emrys/contracts/orchestration/projection.py) also hashes the reference contract; inserting a physical index path there would make that report identity path-sensitive, an effect to review rather than assume.

A provenance sidecar's claimed producer, source hashes, recipe, or origin could change while index member bytes remain fixed. Decide which canonical admitted provenance facts and/or sidecar digest join immutable Run and processing identity, and recheck the bound evidence on resume and inspection. Otherwise the same Run could acquire a different admission meaning without its identity changing.

**Proposed direction:** keep the scientific FASTA/GTF reference meaning unless an independently approved contract decision changes it. Bind supplied-source mode, member fingerprint, and selected admitted provenance facts into immutable Run/processing compatibility, with the chosen path and snapshots at Attempt and Task boundaries. Decide whether same-content relocation is allowed, how retained Tasks and processing reuse readmit the source, and whether generated and supplied sources may ever be reuse-compatible. Changed index bytes or material provenance facts must create a distinct Run or fail continuation; they cannot alter an existing Run.

### F07 — Storage, execution, and recovery

The [Task owner](../../src/emrys/orchestration/run_coordinator/task.py) permits outside-Run native outputs only for the exact Step 00c FAI/dictionary pair. [Attempt materialization](../../src/emrys/orchestration/run_coordinator/materialization.py) indexes admitted external single-file snapshots, not a supplied index-directory manifest. Task input-directory binding detects changed membership and bytes at execution only if Stage 01 declares the directory. [Verified-Task admission](../../src/emrys/orchestration/run_coordinator/task.py) rehashes recorded inputs and checks membership during later inspection. None of these checks alone binds an external directory to the immutable Run.

The [Run contract](../../src/emrys/orchestration/run_coordinator/CONTRACT.md) requires fresh admission for resume and preserves ambiguous locks, partial outputs, and terminal evidence. Shared storage may be unavailable from a compute placement even when a head-node Project path exists. This is a placement and admission failure, not a reason to copy, repair, adopt, or mutate an index.

[Completed-Run inspection](../../src/emrys/orchestration/run_coordinator/inspection.py) re-admits every verified Task, and [Task verification](../../src/emrys/orchestration/run_coordinator/task.py) rehashes its recorded inputs and input-directory membership. If Stage 01 binds the supplied directory, deletion, relocation, or changed bytes after a successful Run can block later integrity admission and processing-source reuse even though old receipts remain. Set the expected lifetime of both index and provenance evidence. A conservative initial policy would require the exact path and bytes to remain available while the Run can be inspected or reused; any relocation or retirement route needs an equal-strength reviewed admission model.

[Direct interactive Run and resume control](../../src/emrys/orchestration/run_coordinator/control.py) previews an `AttemptPlan` and executes the same object after confirmation rather than rebuilding it. A supplied directory could change while the operator reads the preview. Add a fresh content check before Run or successor Attempt publication and at Task entry; a later Task check alone does not prevent stale previewed authority from being published. Slurm head submission delegates full planning to compute, so its admission timing differs.

**Proposed direction:** never publish a supplied directory as a Task output. Bind its exact member inventory and admitted provenance into planning, declare the directory as Stage 01 Task input, and verify that the selected path is readable from the execution placement. Recheck before publication and at existing Task, resume, completed-inspection, and reuse boundaries; state the residual mutation-during-read risk. Because Stage 01 is per sample and the Task/inspection owner hashes each declared directory repeatedly, measure planning, N-sample execution, resume, and completed-Run inspection on representative index size and shared storage before accepting that binding strategy. Any optimization must preserve per-Task and later drift detection. Define retention and clear diagnostics for inaccessible or changed source storage without cleaning the source or ambiguous recovery state.

### F08 — Inventory and truthful reporting

The [profile artifact templates](../../src/emrys/workflow/contracts/local_cmh_v2.json) register fifteen required Stage 00a index artifacts and a Stage 00a validation report at Run-native paths. [Inventory projection](../../src/emrys/contracts/orchestration/artifact_inventory.py) expands the admitted Run profile. The [artifact-index roster check](../../src/emrys/reporting/_artifact_index/core.py) requires the exact fifteen STAR basenames when a Stage 00a scope has rows; absent 00a rows do not trigger that scope check. The [reporting adapter registry](../../src/emrys/reporting/_artifact_index/registry.py) still reads installed processing templates and recognizes the historical generated 00a products. Because rosters come from the Run profile and only present scopes are checked, the existing reader may already accept a supplied profile with no 00a rows. Prove that with a focused fixture before changing the adapter registry; retain its generated-mode support.

[Artifact inspection](../../src/emrys/reporting/_artifact_index/inspection.py) and the [coordinator contract](../../src/emrys/orchestration/run_coordinator/CONTRACT.md) separate admitted artifact facts from downstream reports. A supplied directory is an admitted input, not a Run-produced artifact or Stage 00a validation report. Source provenance needs a truthful place in Run inspection and ordinary summary. The [reporting contract projection](../../src/emrys/contracts/orchestration/projection.py) hashes the reference object; adding a physical supplied-index path there could add a new location dependency. Current Reference records already carry FASTA/GTF snapshot paths, so any location-stability test should hold those paths fixed and relocate only the index, unless a broader Reference contract change is separately approved.

**Open decision:** select one existing contract location for supplied-input provenance and decide what, if anything, appears in artifact inventory. Trace each report reader and independent expectation before changing templates or statuses. Preserve generated-mode rows and avoid a second Artifact Store or report authority.

### F09 — Project and operator experience

[Named Init and validation](../../src/emrys/orchestration/run_coordinator/CONTRACT.md) disclose three STAR settings, preserve a no-write preview, and perform full input admission before creation publishes `project.yaml` last. The [RUNBOOK](../operations/RUNBOOK.md) presents one Project path; the [configuration guide](../../configs/README.md) explicitly says the current `star_index` field does not admit a prebuilt index. The guided writer is also used by [synthetic Project creation](../../src/emrys/orchestration/run_coordinator/synthetic_fixture.py), so its generated default needs protection. An optional source cannot simply become another required `_PROJECT_FIELDS` prompt. A parallel [Init change in PR #316](https://github.com/lab-cats/EMRYS/pull/316) adds conditional EV/PUM1 selection; a future index choice must fit its yes/no guided branches, explicit selectors, and noninteractive creation if that work lands. [PR #320](https://github.com/lab-cats/EMRYS/pull/320) adds browsing for a tool-runtime donor Project, which is a different input from a supplied STAR index. Recheck journey ordering and the onboarding/control seam against the then-current head without conflating those choices.
